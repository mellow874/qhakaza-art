# Phase 0 audit — the collector-intelligence cycle

Audited at `8ec1015`. Every claim below was checked against the code, not
recalled.

---

## Critical defects

### D1 — The public site and every collector see the SAME set of works

This is worse than the brief supposes. The two conditions are not merely
similar; they are **identical**:

```
apps/vera/src/features/catalogue/queries.ts:15
  PUBLICLY_VISIBLE_WORK = { status: 'PUBLISHED', artist: { approved: true } }

apps/collector/src/features/private/queries.ts
  RELEASED_TO_MEMBERS   = { status: 'PUBLISHED', artist: { approved: true } }
```

So publishing a work puts it, in the same instant, on the open web at
`/browse` **and** in every accepted collector's private area. There is at
present **no such thing as private collector inventory**. The distinction the
business rests on does not exist in the code.

Both surfaces also expose `price`.

Affects: `/browse`, `/artists`, `/artists/[slug]`, `/art/[id]` (public) and
`/private/[token]/discover` (collector).

### D2 — Approval is publication, and publication is public

`PUBLISHED` is a single status meaning "visible to everyone". There is no
state between "approved by Qhakaza" and "on the public internet", and no way
to release to one collector rather than all.

### D3 — No audience mechanism exists

No table, column or query anywhere expresses "this work is released to these
collectors". Confirmed: zero occurrences of `audience` in the schema.

### D4 — The collector platform sends collectors into the artist environment

`apps/collector/src/content/collectors.ts:181` links "Artist Intelligence"
out to the artist site. Phase 6 requires this removed.

### D5 — Artist consent is not modelled

Storage and permission are conflated. Nothing records whether an artist
permitted private sharing, partner presentation or public publication, so
Phase 2's visibility engine has nothing to enforce against.

## Derived task list

**Phase 1** — rename identifiers behind a migration; strip `VERA_URL` from
artist-facing naming; remove the collector→artist link (D4).

**Phase 2** — the centre of the cycle:
1. Extend `ArtStatus` with the missing states (additive, as before).
2. New `Audience`, `AudienceMember`, `ArtworkRelease` tables.
3. `ArtistPermission` / `ArtworkPermission` (D5) — the visibility engine must
   consult these.
4. Rewrite `PUBLICLY_VISIBLE_WORK` so the public site shows **editorial only**,
   never available inventory (D1, D2).
5. Rewrite `RELEASED_TO_MEMBERS` to resolve audience membership per collector.
6. RLS policies enforcing release, plus adversarial tests.

**Phase 3** — audience types, matching suggestions from collector preferences.

**Phase 4** — custody records, states, countdown, no double-release.

**Phase 5** — Private Note rebuilt on the Anthropic API, with graceful
degradation and structured extraction.

**Phases 6–10** — as briefed.

## Questions logged

**Q1** The public artist site currently lists works with prices. Removing that
is the correct reading of "must not become a public catalogue", but it is a
visible reduction. Confirm the public site should show **artists and editorial
only**, with no availability or pricing.

**Q2** `SOLD` and `HIDDEN` predate this model. Retain as-is, or fold into
`ARCHIVED`/`SUPERSEDED`?

**Q3** "Wider approved membership" is listed as an audience type. Should the
existing collector cohort be migrated into one such audience so nothing goes
dark on deploy, or should everything become unreleased pending explicit
assignment? The second is safer and more disruptive.
